This article is a short introduction to state machines: what they are, why they matter in software, and three real-world examples that make the shape obvious.

You will get a plain definition, the core parts of a machine, and everyday systems mapped into states and transitions.

What a state machine is

A state machine is a model of behavior with a fixed set of states and a fixed set of legal moves between them. At any moment, the system is in exactly one state. An event arrives. If that event is allowed from the current state, the machine moves to a new state. If it is not allowed, nothing happens — or you reject the event.

The point is not the diagram. The point is the rules: invalid combinations of “where we are” and “what just happened” are impossible to represent by accident.

  • States — mutually exclusive modes (paid, unpaid, cancelled)
  • Events / transitions — the allowed moves between states
  • Guards — extra conditions that must be true to allow a move
  • Actions — optional work that runs on entry, exit, or transition

1. Traffic light

A traffic light is usually in one of three states: green, yellow, or red. The timer (or signal) is the event. From green you can go to yellow. From yellow you can go to red. From red you can go to green. There is no legal jump from green straight to red in a normal cycle.

That is a state machine without software language: few states, strict transitions, one active color at a time. 

green  --timer--> yellow
yellow --timer--> red
red    --timer--> green

2. Online order

An e-commerce order is a better software example. Typical states: created, paid, shipped, delivered, cancelled, refunded.

Payment succeeds only from created. Shipping only from paid. Cancellation may be legal early and illegal after delivery. A refund usually requires a paid or delivered path first. The UI, emails, and warehouse tools all read the same current state and refuse actions that do not belong there. 

created --pay--> paid --ship--> shipped --deliver--> delivered
   |               |
 cancel          refund
   v               v
cancelled       refunded

Boolean flags like isPaid + isShipped + isCancelled can invent nonsense combinations: cancelled and shipped at once. A state machine makes those combinations unreachable.

3. Media player

A player has states people already talk about: stopped, playing, paused, buffering. Press play from stopped → playing. Press pause from playing → paused. Press play from paused → playing. Seeking while buffering has its own rules. 

stopped --play--> playing
playing --pause--> paused
paused  --play--> playing
playing --buffer--> buffering --ready--> playing
any     --stop--> stopped

The interface stays coherent because buttons map to events that are legal only in some states. Pause is disabled when stopped. Play means resume when paused. Same button label, different transition depending on current state.

Why this helps in code

State machines turn messy “if flags and history” into an explicit contract: these are the only modes, these are the only moves, reject everything else. Traffic lights, orders, and media players are everyday versions of the same idea. Once you see that shape, you start finding it in auth sessions, tickets, game turns, and checkout wizards too.
