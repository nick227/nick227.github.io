This article is about nick-webapp-factory, a Claude skill that scaffolds full-stack MVPs with my architecture preferences baked in: spec-first APIs, generated SDKs, copy-first templates, and phase gates so the agent does not rebuild boilerplate from scratch every time.

You will get why I packaged the playbook as a skill, how the OpenAPI spine works, how the template registry saves tokens, and how I actually run a build.

What a Claude skill actually is

A Claude skill follows the standard agent-skills model most providers are converging on. In practice it is a folder: 

skill-name/
  SKILL.md
  scripts/
  templates/
  references/
  assets/

Think of it as a reusable playbook: instructions, examples, scripts, and resources the agent loads when the job matches. Rather than explaining my architecture preferences at the start of every chat, I packaged them once as nick-webapp-factory.

What it builds

The skill scaffolds a production-shaped full-stack MVP. It is extremely biased toward Node.js, Prisma, React, and Vite. You describe the idea, answer four discovery questions, approve a compact MVP definition, and it works through a six-phase build: contract, server, frontend shell, feature pages, polish, documentation.

The architectural spine it enforces looks like this: 

OpenAPI spec  →  generated SDK types  →  typed API client  →  React Query hooks  →  pages
OpenAPI spec  →  fastify-openapi-glue  →  operationId handlers  →  services  →  Prisma

The spec is the single source of truth for routes. No hand-written route registration. No raw fetch in pages. No manually authored generated types. If it is not in the OpenAPI file, it does not exist.

That is the strongest part of the whole thing. Frontend-backend shape drift is the number one way AI full-stack apps fall apart. Spec-first generation removes most of that class of bug before it starts.

The insane part is the template registry

Your agent can regenerate boilerplate from scratch every time. Why would you let it?

The skill has four layers. Orchestration lives in SKILL.md. Phase-specific guides live in references/ and load on demand. Canonical files live in templates/ and get copied verbatim: configs, components, server, SDK, scripts, plugins, frontend packs. Install automation copies packs in, appends env vars, and stages schema and spec patches.

Copy-first is the token saver. Google auth does not need to be reinvented for the five-hundredth time. Harden the templates over time and every future project inherits the improvement. Working on the skill becomes working on your next app.

Antigravity reviewed the skill and landed on the same points I care about: copy-first templates, spec-driven wiring, strict phase gates, a portable SDK layer, and a bias toward action instead of endless summaries. The rigidity adds friction. That is also the point.

How I actually use it

Install it once: 

git clone https://github.com/nicholasrios/nick-webapp-factory \
  ~/.claude/skills/nick-webapp-factory

Claude Code picks it up on the next session. Pre-answer the four discovery questions in one message if you want to skip the interview and go straight to the MVP definition. Approve with something like "build it," then let it run the phases.

Better still, seed the folder first. After a long conversation about the product somewhere else, I ask for a zip of project documents: PRD, personas, site map, flows, feature prioritization, schema outline, design brief, auth roles, integrations. Drop that into the project. Then start the skill.

Mid-build you can still grow the system: 

pnpm factory:add plugin file-upload
pnpm factory:add frontend-pack activity-feed

Plugins cover things like uploads, R2, Google auth, AI chat, image and video generation, Railway, and Vercel. Frontend packs cover themes, feed components, charts, animation, designer workflow, and mock content. The catalogs live in the skill, so extending it means adding a folder and a catalog row, not rewriting the whole playbook.

Why this saves more than time

AI is excellent at filling in code. It is mediocre at holding a long-term architecture in its head across a greenfield build. A skill is how you give it your taste as a durable constraint system.

Phase gates keep it from painting React screens before the contract is real. Templates keep it from hallucinating a new auth stack every Monday. The OpenAPI spine keeps the server and client honest with each other. And when you improve the skill, you improve every app you will generate after that.

That is the feeling I like. Not prompt-and-pray. Portable standards, copied baselines, generated types, and an agent that keeps building until the tests are green.
