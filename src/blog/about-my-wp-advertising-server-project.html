This article is about WP Advertising, a shared ad network I built for WordPress and WooCommerce stores so independent sites can contribute product ads and display each other’s ads without a bidding marketplace.

You will get the network model, how store owners opt in, and why I built it for my own sites first.

A community network instead of an ad marketplace

The network is intentionally simple. There is no bidding system, behavioral targeting, or auction for placement. Participating sites contribute one ad, and the service rotates eligible ads across the network. A store never receives its own ad.

This is not intended to compete with a major advertising platform. It is a cooperative distribution system for independent WooCommerce sites. Each site contributes some of its available space and receives exposure elsewhere in the network.

I think that model is useful because small stores usually have the least leverage in paid advertising. They may not have enough traffic or budget to optimize a conventional campaign, but they can still participate in a shared pool of other merchants.

The plugin needed a service outside WordPress

A WordPress plugin can create and display the ad, but the network needs a shared source of truth. I built a separate Node.js and TypeScript service, hosted on Railway, with Express, Prisma, and MySQL.

Each WordPress site registers with the service and receives an API key. It can then opt in, submit or update its ad, request the next community ad, and send impression or click events. The service also tracks heartbeats so the network knows which sites are still active.

The separation keeps the WordPress side relatively small. The plugin handles the store experience, while the Railway service manages membership, rotation, tracking, and shared network state.

Serving an ad should not slow down the store

The most important technical requirement was keeping the serve path fast. A WooCommerce page should not wait on unnecessary database work just to display a community ad.

Ad requests are served from an in-memory rotation cache. The cache is built from MySQL, refreshed every 30 seconds, and uses a round-robin selection that excludes the requesting site's own ad. The request that chooses an ad does not write to the database.

Impression and click tracking follow a different path. Those events enter an in-memory queue and are written to MySQL in batches. If a database write fails, the events can be requeued rather than delaying the storefront response. Signed event tokens protect the tracking URLs from being rewritten or submitted with arbitrary values.

The service also has separate rate limits for serving ads, recording events, registering sites, and performing administrative work. Health and metrics endpoints expose the state of the cache, event queue, and rate limiter.

I kept the first version deliberately small

The current deployment runs as a single Railway replica because its rotation cache and rate limiter live in process memory. That is a deliberate limit, not something hidden in the deployment. If the network needs horizontal scaling, those responsibilities can move to Redis before additional replicas are added.

For the network I actually have today, the simpler design is easier to operate and less expensive. It still has the boundaries I would need later: the WordPress plugin, the community API, MySQL persistence, cached delivery, and asynchronous event processing.

Is WordPress dead?

In many modern development conversations, yes. New applications are rarely presented as WordPress projects, and Shopify has become the more visible choice for hosted commerce.

In the independent market, the answer is less clear. WordPress remains common because businesses already own their sites, understand the workflow, and can change the code without asking a platform for permission. That installed base still creates room for tools that connect independent stores in new ways.

I would like to build the same kind of exchange for Shopify. The concept is not specific to WordPress: merchants contribute distribution and receive distribution from the network. WordPress simply gave me a direct place to build and test it for myself.

I do not know whether a community WooCommerce ad network becomes a large business. I do think it is a useful model: independent stores sharing reach through infrastructure they can opt into and leave at any time.
