This article is what I actually look for in a pull request: not theater, not style nitpicking as a personality, and not a rubber stamp because the tests are green.

You will get the questions I ask in order, what makes me approve fast, and what makes me send the whole thing back without apology.

Start with the ticket, not the diff

A pull request is a claim that some piece of work is done. The first check is whether the claim matches the ticket. If the title says one thing and the diff does three other things, we do not have a review problem yet. We have a scope problem.

I want the PR description to answer: what changed, why it changed, how to verify it, and what was deliberately left out. Screenshots help for UI. Curl examples help for APIs. “LGTM” from the author does not help.

If I cannot tell what done means from the ticket and the description, I stop reading the code. Clarify first. Review second.

Correctness, contracts, then taste

My review order is deliberate:

  • Does it do the thing? Edge cases, error paths, empty states, auth boundaries.
  • Does it keep the contracts? API shapes, schema fields, event names, permissions, and shared types should not drift in this PR.
  • Is it maintainable? Names, duplication, layering, and whether the next person can change this without archaeology.
  • Are the tests real? Tests that lock the behavior we care about, not tests that restate the implementation.

Style comments come last, and only when they affect reading the code. I am not interested in winning formatting arguments while a null slips into production.

What gets approved quickly

Small PRs with a sharp description. One concern. Obvious verification steps. No mystery files. No “also cleaned up some stuff” attached to a risky change. Shared responsibility already assigned: implementer and reviewer both know they own acceptance.

I also move faster when the author has already left notes on the hard parts. Point at the tricky branch. Say what you almost did instead. Tell me where you are unsure. That is not weakness. That is how review becomes collaboration instead of inspection.

What gets rejected

Silent contract changes. Drive-by refactors inside a feature PR. Missing verification. New abstractions with one caller. Comments that explain the code because the code will not. “We will clean this up later” with no ticket and no owner.

Green CI is necessary and nowhere near sufficient. CI proves the checks we remembered to write. Review asks whether the change is ready to live in the system.

A good pull request makes the next release calmer. That is the bar. If the diff does not leave the codebase easier to reason about than it found it, it is not done yet.
