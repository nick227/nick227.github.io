This article is why I think LangChain is overrated for focused agent work: it looked like the safe corporate choice for an AI-agent-to-API platform, then the abstraction cost outran the product progress.

You will get what paid off, where the framework got in the way, and why I would usually borrow the ideas and write a thinner system myself.

LangChain looks like the safe choice

Agent code can become unreliable very quickly. A demo only needs a prompt and a model call. A real application needs validated inputs, structured outputs, tool definitions, retries, logging, error handling, provider differences, state, and limits on what the model is allowed to do.

LangChain takes those concerns seriously. Its abstractions give teams a shared vocabulary, and its integrations save time when models and providers change. The structured-output support was especially useful for my platform. When a model is selecting and calling an API, “close enough” is not a valid response. The operation and its arguments need to match an actual schema.

I also understand why a larger company would like the consistency. If several teams are building agents, standard tool interfaces and lifecycle hooks can be more valuable than keeping every individual service small. LangChain did not become popular by solving imaginary problems.

The abstraction compounded on us

My problem was not that LangChain could not do what I needed. It was that a straightforward execution path became spread across framework concepts. The prompt, model, tool, state, parser, callbacks, and execution flow each had their own layer. Every layer was reasonable on its own, but together they made the behavior harder to see.

Debugging exposed the cost. When an API call had the wrong arguments, I first had to work backward through framework types and execution steps before I could get to the model response and application decision I actually cared about. The framework was designed to make many workflows possible, while I needed one workflow to be obvious.

I could have built the same platform in about one-third of the code by using the provider SDKs directly and defining a few small interfaces of my own. More importantly, that version would have given me finer control over retries, errors, logging, token usage, and the exact point where an API action was approved or rejected.

The agent loop was not actually that complicated

Underneath the framework, my core process was easy to describe:

  1. Validate the user's request and load the available API operations.
  2. Send the model only the tool schemas it is allowed to use.
  3. Validate the selected operation and arguments against the API contract.
  4. Apply permissions, limits, and any required confirmation.
  5. Execute the request, log the result, and return a clear response.

That loop may branch or retry, but it is still a loop I want to read from top to bottom. I do not need a graph abstraction just because the model can choose between tools. I need explicit state, strict boundaries, and useful logs.

This matters even more for an agent that can operate an API. The risky part is not calling the language model. It is deciding what the model may do, proving that its arguments are valid, and keeping a record of what happened. I want those controls visible in application code instead of distributed through a framework lifecycle.

Simple code is a production feature

Frameworks are often sold as the production-ready option, but simplicity has production value too. A direct implementation is easier to trace during an incident. It is easier to see which request consumed tokens, why a retry happened, and whether an error came from the model, the validator, the remote API, or my own policy.

It is also easier to test. I can give the model adapter a fixed response, pass the result through the same schema validation used in production, and assert that the correct API request would be made. Each boundary has a small contract and there is very little hidden execution behavior between them.

Less code does not automatically mean better code. A homegrown agent can turn into its own undocumented framework if the team keeps adding special cases. The goal is not to reject structure. The goal is to keep only the structure the application has earned.

Use the concepts keep the library

LangChain is still a useful reference for how to shape an agent system. I would keep a standard model interface, typed tool schemas, structured output, explicit state, middleware-style hooks, and consistent tracing. Those are solid patterns whether LangChain owns them or not.

The difference is that I would implement them at the scale of the application. A model adapter can be a small interface. A tool can be a name, description, input schema, and function. A run can have a plain state object and a visible sequence of steps. Logging can wrap each boundary without becoming the architecture.

This approach also makes provider changes less intimidating. The application owns the narrow contract, so switching a model does not require the entire system to speak a framework's language. I only need another adapter that returns the same structured result.

When I would reconsider it

If I were working in an industrial environment with hundreds of agents, I would revisit LangChain and LangGraph. At that scale, shared orchestration, durable state, streaming, human approval, persistence, tracing, and common deployment patterns can justify a substantial platform layer. Multiple teams need conventions, and the cost of everyone inventing a different agent loop can exceed the cost of the framework.

I would also consider it for a genuinely long-running workflow that must pause, survive a failure, resume later, and preserve state across several systems. That is a different problem from a focused service that turns a request into a controlled API call.

The threshold is not literally a certain number of agents. It is the point where coordination and durability become harder than understanding the framework. Until then, the extra abstraction can be an expensive way to avoid writing a small amount of direct code.

“Overrated” does not mean useless

LangChain solves real problems and offers a thoughtful model for building agent systems. I simply think it is recommended too early, before a project has proved that it needs framework-level orchestration.

My preference now is to begin with the smallest explicit loop that can safely do the work. I add typed contracts, validation, logs, limits, and tests from the start. I add durable state or orchestration when the workflow requires it. If the system eventually grows into the kind of operation LangChain was built to coordinate, adopting it becomes an informed trade rather than a default decision.

For most agent projects, that leaves less code, more control, and a system I can explain without first explaining the framework. That is the version I would rather put into production.
