This article is about building Shop-Shop, a DoorDash-style local kitchen and restaurant delivery marketplace: customers discover food through a social-style River feed, vendors run stores and teams, affiliates earn commissions, riders fulfill in-house jobs, and admins keep the rails honest.

You will get the product shape, the pnpm monorepo layout, how contract-driven CRUD and custom marketplace code share one system, and the architecture choices that keep multi-role delivery from turning into glue code.

Food delivery is not a restaurant grid

From a lock-screen widget, delivery looks simple. Under the hood it is a collision of marketplace discovery, order state machines, payouts, geo constraints, and realtime coordination between people who want very different things from the same database.

Shop-Shop is role-first. One deploy serves several products that share inventory and money:

Role What they do
Customer Browse River, search nearby, cart → checkout, track orders, favorite stores/items
Vendor Onboard stores, manage catalog and bundles, fulfill orders, team access, Stripe Connect, store River
Affiliate Referral links, commission dashboard, Connect payouts
Rider In-house delivery assignments and status
Admin / staff Users, vendors, catalog, finance, affiliates, delivery ops, River tooling, audit logs

The home route is not a directory of restaurants. It redirects to River — a scored, diversified discovery feed of store and item posts. Closer to a content product than a yellow-pages list. Store types skew food (HOME_KITCHEN, MEAL_PREP, RESTAURANT, BAKERY, COFFEE, and more). Seeds include a full role matrix plus an Austin kitchen catalog so demos feel real without a live staging city.

Monorepo shape

Everything lives in one pnpm workspace. Apps own I/O. Packages own truth. 

shop-shop/
├── apps/
│   ├── server/          # Fastify API + WebSocket
│   └── web/             # React + Vite SPA
├── packages/
│   ├── db/              # Prisma, services, adapters, seed/CLI
│   ├── domain/          # Policies, domain services, event bus
│   ├── schemas/         # Zod DTOs, defineResource, OpenAPI emit
│   ├── openapi/         # Generated openapi.json
│   ├── sdk/             # typescript-fetch client + frontend helpers
│   ├── realtime/        # Shared WS protocol + client
│   └── shared/          # Pricing/tax/fee constants
├── docs/api/            # Hand-maintained OpenAPI yaml (contract checks)
├── scripts/             # Drift / contract / usage checkers
└── infra/railway/       # API, web, river-ingest deploy configs

Rule of thumb: if it is business rules or persistence, it is a package. If it is HTTP, sockets, or pixels, it is an app. That boundary is what lets us regenerate clients without rewriting store listing geography.

Stack

Frontend is React 18 + TypeScript on Vite 5, React Router 6 with role layouts and lazy pages, TanStack Query for server state, Zustand for client state, Zod + React Hook Form for forms, Tailwind + Radix, Leaflet maps, Stripe Elements for card checkout. Vitest + Testing Library and Playwright for E2E.

A local DX detail that punches above its weight: leave VITE_API_URL empty. Vite proxies /api, River, uploads, and geocode to the Fastify port from the monorepo root .env. Same-origin in the browser. No CORS tax during pnpm dev.

Backend is Fastify 4 with a Zod type provider so request and response schemas are types. JWT + bcrypt, role-aware middleware, Stripe PaymentIntents + Connect, ioredis for checkout idempotency, Pino logging, local uploads or S3-compatible storage. Data is MySQL via Prisma 5. Contracts flow Zod → OpenAPI → typescript-fetch SDK, with a parallel hand-maintained OpenAPI yaml path for drift checks. Realtime sits on /realtime with JWT, ACL’d topics by role for order lifecycle and delivery location/ETA.

Declarative resources, custom where it hurts

Catalog-shaped surfaces — stores, items, carts, bundles, addresses, promotions — are declared once with defineResource: Zod schemas, role access, ownership rules, and hooks like beforeCreate, beforeList, and authorizeAccess for geo browse and activation checks. registerAllResources wires CRUD onto Fastify. The same registry feeds OpenAPI generation. The SDK becomes typed StoresApi, CartsApi, and friends.

That is the boring half done automatically.

River, checkout, delivery dispatch, Stripe webhooks, affiliates, and admin ops are hand-registered Fastify routes with purpose-built services. Honesty matters here: not every endpoint is in the generated OpenAPI/SDK. Resource CRUD is codegen-first. Marketplace economics and logistics are product code, with contract checks where we need them — especially checkout, via yaml and drift scripts.

Orders as a state machine

Order status is not a free-form string. An explicit state machine owns legal transitions: 

PENDING_PAYMENT → PLACED → ACCEPTED → PREPARING → READY
  → OUT_FOR_DELIVERY → DELIVERED
(+ cancel paths)

Checkout pricing constants — tax, delivery fee, platform fee — live in @packages/shared so the UI and server do not invent their own percentages.

Pluggable logistics

Stripe, storage, geocoding caches, and delivery providers sit behind adapters. Delivery is especially intentional: 

DeliveryProvider = IN_HOUSE | DOORDASH_DRIVE | UBER_DIRECT

Shared adapter interface: quote → dispatch → track → cancel. In-house is first-class. DoorDash Drive has a real HTTP client and webhook auth modes (none / basic / hmac; production refuses open webhooks). Uber Direct is stubbed in the registry for a future wire-up — we do not pretend it is live.

Feature domains that carry the product

River — discovery as a feed. Posts, likes, saves, comments, seen-state, cursor pagination, ranking with freshness and diversity. Sources can be manual, auto-store, or auto-product. Ingest CLIs and an admin composer exist so the feed can grow without every vendor becoming a content creator.

Checkout and money — session-style checkout with same-store cart validation, address checks, and delivery mode selection. Card via Stripe PaymentIntents (Connect destination charges + application fee). COD behind feature flags, with commission logic that refuses to accrue on unpaid cash orders. Redis idempotency keys plus Stripe idempotency keys keep double submit from becoming double charge. Vendors and affiliates onboard with Stripe Connect Express. Tips are first-class. Vendor payouts, adjustments, and accounting export give ops a path out of spreadsheets.

Delivery and geo — polygon delivery zones in GeoJSON with fees and minima. Geocoding cache reduces third-party spend. Marketplace search supports radius. Tracking points power Leaflet UIs. Driver and vendor delivery views close the loop for in-house jobs.

Affiliates — not a coupon bolted on. Rate resolution from payout group / per-user override / platform default; attribution via store link, customer referral, or checkout code; caps and audit logs; vendor-side affiliate sales views. Commissions know about payment rails.

Around that: vendor teams and invitations, KYC/KYB-style verification, promotions, store readiness and hours, multipart media upload with client-side compression, favorites, and a rate-limited search surface so marketplace query traffic does not share fate with CRUD.

The codegen loop

pnpm gen:all
# prisma generate
# → DTO generation from Prisma into schemas
# → OpenAPI JSON from resource registry
# → OpenAPI Generator → packages/sdk

pnpm fresh          # reset DB, migrate, gen:all
pnpm start:local    # setup + both apps
pnpm check:api      # drift / contract / usage
pnpm db:seed        # roles, Austin stores, geo caches
pnpm river:initial  # bootstrap feed content

Swagger UI at /docs is the live handshake for resource APIs. Railway configs split API, web, and a river-ingest worker so content jobs do not share process fate with request handlers.

Why this shape

A delivery marketplace fails in two ways: product sprawl (every role gets a bespoke backend) or framework fantasy (everything is a generic CRUD resource until money and trucks show up).

Shop-Shop splits the difference:

  1. Resources + Zod for the stable catalog surface — typed end-to-end, cheap to evolve.
  2. Explicit services for River ranking, checkout idempotency, Connect fees, delivery providers, and affiliate rates.
  3. Shared packages so the SPA, API, and workers argue about one schema and one order machine.
  4. Realtime topics with ACLs so live tracking is not an unbounded broadcast.

The result still feels like one system: change a store list hook, regenerate the SDK, keep Vite same-origin, and ship another role without inventing another stack. If you are building multi-sided logistics with a social discovery surface, the interesting part is not picking React or Fastify. It is deciding which boundaries you refuse to blur.
