This article is a practical NgRx refresher for Angular developers, then a honest look at how NgRx compares to signals, NGXS, Zustand-style stores, and plain Angular services — and how an automated NgRx builder I built removed most of the real pain.

You will get the core elements and how they wire together, when the boilerplate is worth it, how SignalStore and modern Angular shift the conversation, and why generating the store surface consistently beats hand-writing every slice.

Developer refresher: the NgRx pieces

NgRx is Redux for Angular: one central store, immutable updates, and a predictable loop. Once you know the parts, reading a feature becomes pattern matching instead of archaeology. 

Component / effect
    → dispatch(Action)
    → Reducer (pure state update)
    → Store holds new state
    → Selectors derive views
    → Components / effects react

Actions

Actions are events with a type string and optional payload. Prefer createAction / createActionGroup so typings stay honest. 

import { createActionGroup, emptyProps, props } from '@ngrx/store';

export const UsersActions = createActionGroup({
  source: 'Users',
  events: {
    'Load': emptyProps(),
    'Load Success': props<{ users: User[] }>(),
    'Load Failure': props<{ error: string }>(),
  },
});

State + reducers

Reducers are pure functions. Same action + same state always yields the same next state. No HTTP. No router. No side effects. 

import { createReducer, on } from '@ngrx/store';
import { UsersActions } from './users.actions';

export interface UsersState {
  entities: User[];
  loading: boolean;
  error: string | null;
}

export const initialState: UsersState = {
  entities: [],
  loading: false,
  error: null,
};

export const usersReducer = createReducer(
  initialState,
  on(UsersActions.load, (state) => ({
    ...state,
    loading: true,
    error: null,
  })),
  on(UsersActions.loadSuccess, (state, { users }) => ({
    ...state,
    entities: users,
    loading: false,
  })),
  on(UsersActions.loadFailure, (state, { error }) => ({
    ...state,
    loading: false,
    error,
  })),
);

Register the feature when you boot the store (standalone or NgModule): 

provideStore(),
provideState('users', usersReducer),
provideEffects([UsersEffects]),

Selectors

Selectors are how consumers read. Memoize derived views so templates and effects do not recompute junk. 

import { createFeatureSelector, createSelector } from '@ngrx/store';

export const selectUsersState = createFeatureSelector<UsersState>('users');

export const selectUsers = createSelector(
  selectUsersState,
  (s) => s.entities,
);

export const selectUsersLoading = createSelector(
  selectUsersState,
  (s) => s.loading,
);

Effects

Effects own side effects: HTTP, navigation, toasts. Listen to actions, do the impure work, dispatch success/failure actions. Keep reducers boring. 

import { inject, Injectable } from '@angular/core';
import { Actions, createEffect, ofType } from '@ngrx/effects';
import { catchError, map, of, switchMap } from 'rxjs';
import { UsersActions } from './users.actions';
import { UsersApi } from './users.api';

@Injectable()
export class UsersEffects {
  private readonly actions$ = inject(Actions);
  private readonly api = inject(UsersApi);

  load$ = createEffect(() =>
    this.actions$.pipe(
      ofType(UsersActions.load),
      switchMap(() =>
        this.api.list().pipe(
          map((users) => UsersActions.loadSuccess({ users })),
          catchError((err) =>
            of(UsersActions.loadFailure({ error: String(err) })),
          ),
        ),
      ),
    ),
  );
}

Consuming in a component

readonly users = this.store.selectSignal(selectUsers);
readonly loading = this.store.selectSignal(selectUsersLoading);

ngOnInit() {
  this.store.dispatch(UsersActions.load());
}

That last line matters: modern NgRx already meets Angular signals at the consumption edge via selectSignal.

How this relates to Angular signals

Signals are Angular’s built-in reactive primitives for local and component-tree state. They shine for UI state, derived view models, and fine-grained updates without RxJS ceremony.

NgRx still earns its keep for shared, audited, multi-feature application state: who changed what, when, and through which action. Effects, DevTools time travel, and a single event log are still the strong arguments.

The current Angular picture is usually mixed:

  • Local form / dialog / tab state → signals (or signal-based inputs/outputs)
  • Cross-feature domain state with clear event history → NgRx Store or NgRx SignalStore
  • Bridge store → template with selectSignal so templates stay in signal-land

SignalStore is NgRx’s answer to “less wiring, still disciplined.” It sits closer to a typed service-with-rules than classic actions/reducers/effects files. Classic Store remains the scale pattern many enterprise apps already standardized on. Neither erases the other overnight.

Boilerplate: NgRx vs everything else

People do not hate NgRx because reducers are hard. They hate the file tax.

Angular state management approaches
Approach Ceremony Strength Weakness
Angular service + BehaviorSubject / signals Low Fast to start; natural DI Ad-hoc patterns; hard to audit at scale
Zustand (React mental model) Very low Tiny store, fewer files Not Angular-native; different ecosystem instincts
NGXS Medium Class actions / fewer explicit pieces Less Redux purity; smaller ecosystem than NgRx
NgRx classic Store High Explicit events, DevTools, effects isolation Actions + reducer + selectors + effects + models every feature
NgRx SignalStore Medium-low Typed store without Redux file scatter Teams still need conventions around side effects

A Zustand slice can be one file. An Angular service with a few signals can be one injectable. Classic NgRx often means four to six files and naming discipline before you have drawn a single pixel. That cost buys predictability when many teams touch shared domain state — and it buys agony when every feature reinvents naming, folder layout, and load/success/failure shape by hand.

Relative to NGXS, NgRx is more verbose and more explicit. Relative to services, NgRx moves side effects out of “whatever the injectable felt like doing.” Relative to Zustand’s vibe, NgRx looks heavy because it is heavy on purpose: event sourcing for UI decisions.

So the question becomes: if the architecture is good, can we stop paying the typing tax every sprint?

The NgRx builder: remove the pain, keep the pattern

That is why I built an automated NgRx builder. The goal was not to invent a new state library. It was to make classic NgRx feel less like a tax and more like a machine:

  • Describe a feature once — entity name, fields, async operations, list vs detail shapes
  • Generate the matching actions, reducer cases, selectors, effects stubs, and registration hooks
  • Enforce one naming convention, one load/success/failure shape, one folder layout
  • Leave humans to write the real API calls, business rules, and UI — not rename loadUsersSuccess for the fiftieth time

In practice that is what simplified developer work. Onboarding stopped being “copy the users feature and pray.” Reviews stopped arguing about file layout. Quality became consistent because the boring surface was identical every time. Speed went up because the main pain of NgRx is not architecture — it is repeating architecture correctly.

The builder also encoded the lesson every senior Angular team learns too late: store codegen only works if the output is opinionated. Soft templates that let every team invent a dialect recreate bug hell inside the Redux folder. Hard conventions — same action groups, same error channel, same selector names — are the product.

Once generators own the scaffolding, NgRx’s remaining cost is decision cost: What belongs in the global store versus a local signal? Which effects need cancellation (switchMap) versus parallel fan-out? Those are good engineering problems. Generating five nearly identical files is not.

When I still reach for NgRx

I reach for NgRx (classic or SignalStore) when:

  • Multiple features share the same domain state
  • We need a clear event history for debugging
  • Side effects need a standard home outside components
  • The team is large enough that conventions matter more than personal taste

I reach for signals / services when:

  • State dies with the component
  • There is no cross-feature replay story
  • A thin facade over HTTP is enough

And I treat generators as mandatory once the team standardizes on classic NgRx. Without them, the library tax leaks into every estimate. With them, you keep the discipline and ship store surfaces that look like they came from the same factory — because they did.

NgRx is not outdated because signals exist. Signals shrunk the surface area where a global store is necessary. For the surface area that remains, either accept the boilerplate, switch to a lighter store style, or automate the Redux files until humans only write the interesting parts. That last option is how I made NgRx livable on real teams.
