This article is about AutoImage, the image-batch system I have rebuilt since 2022: controlled prompt variation, fail-fast queues, provider switching, and organized review so studio-quality harvests stay usable at volume.

You will get the prompt-builder approach, how I protect tokens on bulk runs, what changed across providers since DALL-E 2, and where the public tool stands now.

The prompt builder is the best part

Sending the same request hundreds of times was easy. To make those requests different without losing the intended subject or style, I built a database of terms grouped by type. Prompts contain placeholders such as {colors}, {fashion_style}, or {camera_angle}, and each placeholder receives a value from its matching group. 

{subject} + {fashion_style} + {colors} + {camera_angle}
     ↓              ↓             ↓             ↓
 selected subject   streetwear    pastel blue   low angle

The groups keep the random choices within useful boundaries. A color placeholder always produces a color. A camera-angle placeholder always produces a camera angle. The details change while the prompt keeps the same basic structure.

Every manual run gave me another ten or twenty terms to save. The database eventually grew beyond one thousand entries, including basic colors, pastel colors, hair colors, camera angles, fashion styles, strange dreams, and mythological monsters.

The current process goes beyond selecting stored words. AutoImage uses Compromise.js and the Datamuse API to work with word types and related terms. An LLM then expands the assembled prompt while following a narrow set of rules: preserve the idea, keep the subject in focus, and add enough visual detail for the image model. The database controls what may vary, language processing finds alternatives, and the LLM improves how the final idea is expressed.

The first priority is protecting the tokens

In this project, tokens and API requests represent real spending. A bulk run can become expensive if a failed request keeps retrying or one user fills the entire queue. I put generation work behind a queue that controls concurrency, priority, and per-user rate limits. A single user cannot consume all available provider capacity, and a large batch cannot send every request at once.

“Fail fast” does not mean that every error is abandoned immediately. The system first separates temporary failures from requests that are unlikely to succeed:

  • Network errors, rate limits, timeouts, and temporary server errors can be retried.
  • Retries use exponential backoff, starting at 500 milliseconds and doubling with a small amount of random jitter.
  • Invalid client requests and content-policy failures stop immediately rather than spending more tokens on the same work.

Every queue event is logged. Because many batches run unattended, the logs need to show whether a problem came from the prompt, my application, a rate limit, or the provider itself. The admin queue monitor exposes waiting and active jobs, completed and failed counts, per-user throttling, and the stored queue history. One bad job can be inspected later without blocking the rest of the batch or repeatedly hitting a paid endpoint.

About my system design

A provider response is only the middle of the generation process. Before an image appears in a user's feed, AutoImage has to validate the request, protect the user's balance, store the file, and leave a reliable accounting record.

  1. The prompt is checked for length and disallowed content.
  2. Optional enhancement and semantic substitutions are applied.
  3. The user's credit balance is checked before the work enters the queue.
  4. The selected provider generates the image.
  5. The returned image data and file size are validated.
  6. The image is uploaded to Cloudflare R2 object storage.
  7. Credits are deducted atomically and recorded in the credit ledger.
  8. The image and its metadata are saved to MySQL through Prisma.

The credit ledger matters because a displayed balance is not enough for paid generation. Every purchase, promotion, and image deduction needs a record that can be audited. The user's current balance is convenient to read, but the ledger explains how that balance changed.

Cloud storage solved another practical issue. Providers often return base64 image data, which is not how I want to serve a permanent gallery. AutoImage validates the result, moves it into Cloudflare R2, and stores the image record separately in the database.

Image providers and local diffusion

DALL-E 2 was my first serious playground for image generation, and OpenAI was also where I began learning how LLMs could improve prompts. The images were rough compared with current models, but the API provided a useful place to learn prompt structure, batching, rate limits, and failure handling.

To increase the usage limits on my account, I had to increase my OpenAI spending. That made accounting and rate limiting early requirements. It was not enough for the application to submit a valid request; it also needed to know how much work a user could send and what each successful image should cost.

I later tested Gemini, Grok, Dezgo and FLUX, along with diffusion models on my local RTX 3060. I currently prefer Gemini when final quality matters most. I use local diffusion for development because I can test the pipeline without paying for every image. Dezgo and FLUX remain useful for lower-cost batch work, including YouTube thumbnails.

AutoImage keeps provider-specific code behind a common interface. Provider and model records live in the database, including their cost per image and whether they are currently active. That means I can enable a model, disable one that is unavailable, or change what users can select without rebuilding the interface or deploying new frontend code.

Where AutoImage is now

The latest public version is AutoImage. It has grown from a personal batch script into a multi-user application with image storage, credits, billing, galleries, search, moderation, and an admin view of the generation queue.

I still use the dynamic prompt builder regularly. Generating ten structured variations gives me a useful comparison set. I can see which terms helped, discard weak images, and use the strongest result to guide the next run.

The providers will continue to change. The part I expect to keep is the process around them: control what can vary, decide which failures deserve a retry, account for every paid operation, preserve the output, and leave enough information to understand the run afterward.
