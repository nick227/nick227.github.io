This article is a practical guide to running LTX local video generation: how to generate short clips from text or a reference image on your own GPU, and how to keep the model loaded as an HTTP service your apps can call.

You will get hardware expectations with a card comparison table, a CLI-first setup based on my ltx-env project, the FastAPI persistent server pattern, common LTX model checkpoints on Hugging Face, and the failure modes that waste an evening if nobody warns you.

What you are installing

LTX-Video (Lightricks) is an open diffusion / DiT-style video model. Through Hugging Face Diffusers you get two pipelines:

  • LTXPipeline — text-to-video
  • LTXImageToVideoPipeline — animate a still with a motion prompt

My project wraps those pipelines two ways:

  • generate_ltx.py — one-shot CLI (loads weights every run)
  • server.py — FastAPI service that loads once, shares weights between text and image pipelines, and serves MP4s over HTTP 
prompt or image
    → LTX pipeline (diffusers)
    → frames
    → export MP4 (ffmpeg / imageio-ffmpeg)
    → file path or /media URL

Expect first-run model downloads (multi-GB), CUDA GPU time measured in tens of seconds to a few minutes per clip depending on card and settings, and quality that improves with better prompts, valid frame counts, and distilled or newer checkpoints when you harden the stack.

Hardware: what “local” actually costs

Local LTX is a GPU product. CPU-only PyTorch can technically crawl through diffusion steps; for video it is not a serious workflow. NVIDIA CUDA cards with recent drivers are the default path. My server path uses enable_model_cpu_offload(), VAE-friendly settings, and bf16/fp16 weights to reduce VRAM pressure — you still want a capable CUDA device.

Approximate wall-clock for one teaching workload — 640×480, 49 frames (~2s at 24fps), ~25 steps, LTX-class 2B/distilled style settings — on a quiet machine. Treat these as order-of-magnitude planning numbers, not a lab bench certificate. Resolution, steps, 13B vs 2B, and distillation change everything.

LTX generation hardware benchmarks
Hardware Memory Approx. time / clip Notes
CPU only (modern desktop) system RAM 1–4+ hours Not practical for iteration
RTX 3060 / 4060-class 8–12 GB ~3–8 min Use offload, smaller res/frames; expect swaps
RTX 4070 / 4080 12–16 GB ~90 s–4 min Solid local iteration for short clips
RTX 4090 24 GB ~20–90 s Community sweet spot; often near-real-time on distilled LTX settings
RTX 5090-class ~32 GB ~15–60 s Higher bandwidth/compute when drivers/stack are ready
A100 40/80 GB 40–80 GB ~25–120 s Datacenter throughput + headroom for larger jobs
H100 80 GB 80 GB ~15–90 s Strong tensor performance; infra cost is the tax
NVIDIA DGX Spark (GB10 Grace Blackwell) 128 GB unified ~30 s–3 min DGX Spark trades peak bandwidth vs a 4090 for huge coherent memory — better when larger checkpoints / concurrent tools must stay resident

Rule of thumb: buy bandwidth and VRAM for iteration speed; buy unified memory (Spark-class) when the checkpoint or multi-model workflow does not fit a consumer card. For day-to-day LTX clip loops, a 4090-class GPU is still hard to beat on dollars-per-minute.

Install and first CLI video

git clone <your-ltx-env-repo>
cd ltx-env
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip

# Install the CUDA build of torch that matches your drivers, then:
pip install diffusers transformers accelerate \
  fastapi uvicorn pydantic pillow numpy requests imageio-ffmpeg

PyTorch install lines change by CUDA version — follow the current matrix on pytorch.org.

Generate with Diffusers’ LTX pipelines (this is the path my generate_ltx.py uses against Lightricks/LTX-Video): 

python generate_ltx.py \
  --prompt "A paper boat sailing across a rain-covered city street" \
  --width 640 \
  --height 480 \
  --frames 49 \
  --steps 30 \
  --seed 42 \
  --output media/paper-boat.mp4

Hard constraints from the model / server validation:

  • Width and height should be multiples of 32
  • Frame count should satisfy (frames - 1) % 8 == 0 (examples: 9, 17, 33, 49, 65, 97) — prefer these over casual numbers like 30
  • Seed for repeatable experiments

Image-to-video is the same entrypoint with --image. Prompt for motion (“looks up and waves”) more than re-describing the still. Match aspect ratio when you can; wild crops encourage morphing. 

python generate_ltx.py \
  --prompt "The character looks up, smiles, and waves gently" \
  --image media/reference.jpg \
  --width 640 \
  --height 480 \
  --frames 49 \
  --output media/animated-reference.mp4

Persistent FastAPI service

The CLI reloads multi-GB weights every process. The server loads once, keeps text-to-video and image-to-video pipelines sharing components, and returns telemetry (runtime, peak VRAM, motion metrics) with the file. 

export LTX_BASE_DIR="$PWD"
export MEDIA_DIR="$PWD/media"
export API_TOKEN="replace-with-a-long-random-token"
export HOST="127.0.0.1"
export PORT="8000"

source .venv/bin/activate
python server.py

First boot downloads and loads the checkpoint — plan for that delay. Then: 

curl http://127.0.0.1:8000/health
curl http://127.0.0.1:8000/ready
# {"status":"ready"} when weights are loaded
curl -X POST http://127.0.0.1:8000/generate \
  -H "Authorization: Bearer replace-with-a-long-random-token" \
  -H "Content-Type: application/json" \
  -d '{
    "req_id": "my-first-video",
    "prompt": "A red fox running through fresh snow at sunrise",
    "preset": "fast",
    "frames": 49,
    "seed": 42
  }'

/generate stays open until export finishes. Poll /progress/<req_id> for loading → generating → saving → completed / failed. My service accepts one active generation at a time; others get 409 BUSY — retry later or put a queue in front for production.

Image inputs: omit for text-to-video; pass a path under LTX_BASE_DIR; or a data:image/...;base64,... value. Paths are the server’s filesystem, not your laptop’s, when the client is remote.

LTX generation presets
Preset Generation size Steps Delivery
fast 640×480 25 Direct export
balanced 768×576 35 Downscaled to 640×480
quality 768×576 40 Downscaled to 640×480

Also tune motion_intensity (subtle / medium / high), guidance_scale, negative_prompt, frame_rate, and seed. 

const response = await fetch("http://127.0.0.1:8000/generate", {
  method: "POST",
  headers: {
    Authorization: `Bearer ${process.env.LTX_API_TOKEN}`,
    "Content-Type": "application/json",
  },
  body: JSON.stringify({
    req_id: crypto.randomUUID(),
    prompt: "A small robot planting flowers on a rooftop",
    preset: "balanced",
    frames: 49,
    motion_intensity: "medium",
  }),
});
const result = await response.json();
if (!response.ok) throw new Error(result.error?.message ?? "generate failed");
console.log(result.url ?? result.output_path);

Give HTTP clients a long timeout. Handle 409. Poll progress from the UI if the request stays open too long for your gateway.

Common models and resources

  • Lightricks/LTX-Video — main model card and checkpoints (including 2B / 13B and distilled / fp8 variants)
  • github.com/Lightricks/LTX-Video — upstream training / inference codebase
  • Diffusers LTX docs — LTXPipeline / LTXImageToVideoPipeline
  • Distilled and fp8 siblings on the same org (e.g. 13B distilled for faster loops, 2B distilled for lighter VRAM) — pick from the model card table rather than guessing filenames
  • Newer LTX lineage (LTX-2 / LTX-2.3) exists for production-oriented stacks; this guide focuses on the open Diffusers LTX-Video path my local service uses

For validation, my repo includes test_baseline.py, test_phase1.py, and run_tests.sh — they perform real inference, so they need GPU, weights, and ffmpeg.

Troubleshooting

  • CUDA unavailable — drivers, nvidia-smi, CUDA-matched torch wheel
  • OOM — lower width/height, frames, steps; close other GPU apps; keep CPU offload
  • Model download fails — disk, network, HF auth
  • 400 on dimensions / frames — multiples of 32; (frames - 1) % 8 == 0
  • 401 — bearer token must match API_TOKEN
  • 409 — another job is running
  • Export / downscale fails — install system ffmpeg on PATH

Check server.log for load and request errors. Before exposing the service: strong token, HTTPS reverse proxy, bind to localhost unless remote is intentional, a durable queue instead of one in-memory lock, rate limits, retention rules, and no absolute server paths in public responses.

What “done” looks like

You have a CUDA machine, a venv with Diffusers LTX, a first MP4 from the CLI, a persistent server that answers /ready, authenticated /generate calls that write into MEDIA_DIR, and an app that can tolerate long requests and 409s. After that, upgrade checkpoints, add a job queue, and decide whether your next dollar buys a faster consumer GPU or a high-memory Spark-class box for bigger resident models.
