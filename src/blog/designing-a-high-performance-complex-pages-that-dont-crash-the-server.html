This article is about building high-performance end-to-end pages when the product is busy: posts, joins, status changes, media uploads, and a chronological feed that has to stay fresh without melting the database.

You will get why assembling a live river from dozens of source tables on every request is madness, how writers plus a worker and outbox fix that, when a simpler same-transaction projection is enough, and how to keep clients on a single cheap read.

The social feed problem

Picture a social product. People are posting. People are joining groups. Statuses flip. Media finishes uploading. Mentions land. Reactions stack up. The home page wants one thing: a chronological fresh feed.

If you build that river fresh from the source tables on every request, you are asking the database to reassemble history under load. A realistic version is a massive union of multi-join queries across domains that were never meant to be one page. 

-- Conceptual madness (do not ship this as your feed)
SELECT * FROM (
  SELECT p.id, p.created_at, 'post' AS kind
  FROM posts p
  JOIN users u ON u.id = p.author_id
  LEFT JOIN media m ON m.post_id = p.id
  WHERE ...

  UNION ALL

  SELECT j.id, j.created_at, 'join' AS kind
  FROM memberships j
  JOIN users u ON u.id = j.user_id
  JOIN groups g ON g.id = j.group_id
  WHERE ...

  UNION ALL

  SELECT s.id, s.created_at, 'status' AS kind
  FROM status_events s
  JOIN users u ON u.id = s.user_id
  WHERE ...

  -- plus uploads, mentions, reactions, ...
) river
ORDER BY created_at DESC
LIMIT 50;

Every refresh locks attention across many tables, fills working memory with expensive joins and sorts, and repeats that work constantly for every scrolling client. It would be madness. The page is complex. The read path should not be.

Writers drop notes; workers build the page

Writers are anything that changes or happens: create post, accept join, finish upload, change status. On a major enterprise system, that write often dumps a request into a RabbitMQ-style hopper. Kafka, service buses, CDC, triggers, and job tables are variations of the same idea.

For an MVP, the hopper can be an outbox table in the same database. The write transaction stores the domain change and a durable note that work remains. Meanwhile a worker watches only that table. Anything it sees gets validated: is this valid river content? If yes, the worker formats a RiverItem with all the time in the world, because no browser is waiting on that request.

That worker can run on a different machine than the web server. It can do aggregate calculations, hydrate display names, attach media URLs, and finally write a pristine row into something like RiverItem. Clients hitting the river API then get a simple single-read result: no joins, no unions, no SQL puzzle on the hot path. 

Domain write
   ↓  (same transaction)
Outbox / queue note
   ↓
Worker validates + projects
   ↓
RiverItem table  →  optional Redis / memory cache
   ↓
River API: SELECT … FROM RiverItem ORDER BY created_at DESC LIMIT n

Transactional outbox versus same-transaction MVP

A transactional outbox is relatively low cost and sets you up for separate worker infrastructure later. It may be overkill for throwaway prototypes. For a chronological MVP, the simpler path is: 

Domain write → RiverItem update in the same transaction

That skips hoppers and lag. It also couples request latency to projection work and makes replay, multiple consumers, and failure isolation harder.

The fuller outbox approach adds:

  • Outbox events
  • Per-consumer delivery records
  • Polling or stream consumption
  • Retry handling
  • Deduplication
  • Projection lag
  • Worker lifecycle and monitoring

In exchange, it provides:

  • Reliable asynchronous projection
  • Replay and rebuilding
  • Isolation from request latency
  • Consistent processing across domains
  • Future consumers such as search and notifications
  • A record of failed delivery

The main question is not traffic volume. It is whether you expect the River to become an important cross-domain system. If yes, pay for the outbox early. If the feed is a thin MVP feature, same-transaction projection can be honest scaffolding.

What the hopper can look like

Teams name this layer differently. The pattern is the same: durable intent that a worker will process.

  • Kafka infrastructure
  • Service-bus libraries
  • Database triggers
  • Change-data-capture systems
  • Framework event publishers
  • Queue-specific job tables
  • Vendor integration middleware
  • Application names such as Event, Job, Message, or PendingTask

In my MVP preference, the outbox table lives in the same database as the write. That keeps “domain change + pending work” atomic without introducing a broker on day one.

After RiverItem, stop making clients think

Once the projected table exists, the API is boring on purpose. Read RiverItems in chronological order. Paginate. Return a display-ready shape.

At that point you do not even need SQL on every hit. The worker, or a thin cache warmer, can preload the last N results into server memory (node-cache) or into Redis. Limit how often clients touch the actual database. The expensive thinking already happened offline. 

Writer domains          Worker box              Read path
-----------             ----------              ---------
posts / joins    →      validate event   →      RiverItem
uploads/status   →      format item      →      Redis / memory
mentions/...     →      write projection →      /river?cursor=

High-performance pages are prepared pages

Complex products create constant change. High-performance pages do not recompute that universe on every scroll. They separate writers from readers, project a chronological product ahead of time, and serve a single cheap artifact.

Build the river before the user asks for it. Then the page can feel fresh without asking twenty tables to audition for every request.
