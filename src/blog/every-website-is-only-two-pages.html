This article argues that most websites are only two page types: an index of items and the item page. It is an oversimplification, but it is useful for systems design, visual design, and API shape.

You will get the two shapes drawn out, several product use cases mapped onto them, and how that pattern should show up in the API. 

INDEX                              ITEM
┌─────────────────────┐            ┌─────────────────────┐
│ search / filters    │            │ one subject         │
│                     │   pick →   │ title · status · id │
│ row                 │            │                     │
│ row                 │            │ detail              │
│ row                 │            │ actions             │
│ row                 │            │ related index ↓     │
│ …                   │            └─────────────────────┘
└─────────────────────┘

An index answers: what exists, and which one do I care about next? An item page answers: what is this, and what can I do with it? Different costumes. Same jobs.

Looks like Index Item

Online store

A hat store is the cleanest version of the idea. The catalog is an index. The product page is the item. Everything else is decoration around that pair. 

/hats
  [ beanie ] [ fedora ] [ cap ] [ cowboy ]
         │
         └─ click fedora → /hats/fedora
                              price
                              sizes
                              add to cart
                              reviews  ← nested index

Category pages, search results, and “similar hats” are still indexes. Cart is an index of line items. Checkout opens one order item. You do not need a new page archetype for each of those nouns.

Social feed

A feed is an index of posts. Opening a post is the item page. Comments are a nested index under that item. Profiles are item pages with their own nested indexes: posts, followers, media. 

/feed                         /posts/1842
┌──────────────────┐          ┌──────────────────────┐
│ post A           │──open──▶ │ post A               │
│ post B           │          │ body                 │
│ post C           │          │ like · share         │
└──────────────────┘          │ comments:            │
                              │   c1                 │
                              │   c2                 │
                              └──────────────────────┘

Notifications are another index. Each row points at an item that already exists somewhere else. The product gets louder when teams invent a unique layout for every social noun instead of strengthening these two.

Support tickets

Agents live in a queue. That queue is the index: status, priority, assignee, waiting time. The ticket page is the item: description, customer, timeline, actions. 

INDEX /tickets                 ITEM /tickets/90210
#   status   wait   owner      subject: Billing failed twice
902 open     4m     Ana        customer: acme-18
911 pending  21m    —          timeline:
918 open     1h     Jon          note · reply · event
                               actions: assign · resolve

Bulk assign and bulk close belong on the index. Reply, escalate, and resolve belong on the item. If an action needs the full ticket body to make sense, it wanted the item page.

Admin and CRM

Admin software is indexes all the way down until you open a record. Customers, invoices, employees, audit events. Same table pattern, different columns. 

/customers                     /customers/acme
┌───────────────┐              ┌─────────────────────────┐
│ Acme          │──open──────▶ │ Acme                    │
│ Globex        │              │ contacts · billing      │
│ Initech       │              │                         │
└───────────────┘              │ orders     ← nested index
                               │ invoices   ← nested index
                               │ tickets    ← nested index
                               └─────────────────────────┘

Nested indexes stay under the item unless people truly need to start from that list globally. “All invoices across all customers” is its own index. “Invoices for Acme” is part of the Acme item.

Chat and create flows

A thread is an index of messages. The composer is the item page for a message that does not have an id yet. Create screens in general are item pages before persistence: new post, new ticket, new product. Same form shape as edit when you can manage it. 

/threads/42
┌─────────────────────────────┐
│ msg 1                       │  ← index rows
│ msg 2                       │
│ msg 3                       │
├─────────────────────────────┤
│ [ write next message ]      │  ← item with no id yet
└─────────────────────────────┘

What the API should look like

If the product is only indexes and items, the API should feel that way too. 

GET    /resources              index
GET    /resources/:id          item
POST   /resources              create item
PATCH  /resources/:id          update item
DELETE /resources/:id          remove item
GET    /resources/:id/children nested index

Shared list contracts, shared detail contracts, shared pagination, shared error shapes. When a new screen appears, ask which collection it lists and which entity it opens. If you cannot answer, the screen is probably confused.

Spec-first designs benefit immediately. The frontend stops growing a new fetch style for every page, and the server stops inventing a snowflake route for every noun.

Every website is only two pages. Make the index excellent at choosing. Make the item excellent at acting. Nest related indexes under the item. Keep true exceptions rare: login, pricing, legal. Then notice how little else you needed.
