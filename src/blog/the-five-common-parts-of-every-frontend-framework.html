This article is about the five common parts inside every mainstream frontend framework. React, Angular, and Vue look different on the surface. Underneath they solve the same high-level problems: bind data to UI, manage state, and respond to user events without turning the DOM into a manual chore.

You will get the five shared parts, a naming map across frameworks, a deeper look at state and the helper libraries around it, and how this whole product category matured over the last ten years.

What they all solve

Before these tools, a lot of app code was glue: find a node, set its text, attach a listener, remember to clean it up, hope nothing drifted. Frameworks take that glue and make it declarative. You describe the UI from state. The framework keeps the screen honest when state changes.

Three jobs show up everywhere:

  • Bind content to UI — turn data into elements and keep them in sync
  • Manage state — know what is true right now in the app
  • Manage user events — clicks, typing, submits, and route changes that update that truth

Everything else is packaging around those jobs.

1. Components

Components are the unit of composition. A button, a form, a page section. You assemble products from smaller pieces with inputs in and events out.

React calls them function components. Vue has SFCs and setup scripts. Angular has components decorated with metadata. Same job: isolate a slice of UI and reuse it.

2. Templates and binding

This is how content reaches the screen. You declare what should appear for the current state. The framework patches the DOM.

React returns JSX from render logic. Vue and Angular lean on HTML-like templates with binding syntax. Lists, conditionals, and text interpolation are the daily bread. When state changes, the bound UI updates without you hand-editing nodes.

3. State

State is the app’s memory: form fields, fetched records, selected tab, auth session, cart lines. Local state lives next to one component. Shared state is lifted or stored in a dedicated layer so distant screens stay aligned.

4. Events

Users poke the machine. Clicks, keypresses, submits, drag gestures. Event handlers translate those into state updates or commands. Frameworks normalize how you attach handlers and how you pass data upward from child to parent.

5. Lifecycle and effects

Real apps talk to servers, set timers, subscribe to sockets, and sync the URL. That work is not rendering. Lifecycle hooks and effect APIs say when to start, restart, and clean up side work as dependencies change.

Naming differences

The vocabulary changes. The roles do not.

Idea React Vue Angular
UI unit Component Component / SFC Component
Inputs from parent props props / defineProps @Input()
Outputs to parent callbacks / props emit / defineEmits @Output() EventEmitter
Local state useState / useReducer ref / reactive fields + signals
Side effects useEffect watch / watchEffect hooks / RxJS / effects
List binding map in JSX v-for *ngFor / @for
Conditional UI && / ternary v-if / v-show *ngIf / @if
DOM event onClick @click (click)

Learn one column deeply and the others become translation, not reinvention.

Deep dive: state, helpers, and design

State design is where products get calm or chaotic. A useful split:

  • Server state — data that lives in an API: users, orders, posts
  • Client state — UI-only truth: modal open, wizard step, theme
  • URL state — filters and ids that should survive refresh and share

Helper libraries grew up around that split. React Query, SWR, and Apollo treat server data as a cache with loading and error semantics. Redux, Zustand, Pinia, and NgRx handle shared client state and predictable updates. Form libraries own field state so pages do not invent another half-broken form model.

Design strategies that hold up:

  • Keep server state out of giant global stores when a query library already solves it
  • Lift state only as far as sharing requires
  • Prefer derived values over duplicated copies
  • Put shareable filters in the URL
  • Make writes explicit: one event, one state transition, one obvious place to debug

Signals and finer-grained reactivity are the recent convergence: update less of the tree when one field changes. Different brands, same pressure toward precise subscriptions.

Ten years of maturation

A decade ago the fight was still “who owns the DOM” and “do we need a framework.” Then it became build tooling wars, then state management wars, then meta-framework wars. The dust settled into a clearer stack: components, a compiler or bundler, a router, a server-state library, and optional islands or SSR for first paint.

TypeScript moved from optional to default. Design systems became real packages instead of copied CSS. Testing shifted toward components and user flows. React, Angular, and Vue all grew official or semi-official answers for routing, forms, and data fetching instead of leaving every team to invent a house style from blog posts.

The biggest maturity signal is boredom in a good way. New apps start from known parts. The interesting work moved up into product design, performance budgets, and domain modeling — not into rewriting click handlers by hand.

Takeaway

Every frontend framework is five parts in a trench coat: components, binding, state, events, and effects. Learn the parts once. Translate the names as needed. Put state where it belongs, and let the helper libraries do the jobs they were built for.
