This article is my working rule for backend and product work: write the contract before the code, then let the code obey it instead of inventing a second truth.

You will get why I start with OpenAPI and schema, what belongs in that contract, and how this changes the order of implementation for a team.

Code without a contract invents one anyway

Every endpoint has a contract, whether you wrote it down or not. Status codes, error shapes, pagination, auth headers, nullability, field names. If those decisions live only in route handlers and frontend fetch calls, the team is maintaining folklore.

Folklore drifts. One client treats a missing field as null. Another treats it as an empty string. The server returns 400 in one place and 422 in another for the same class of failure. Nobody is lying. They are all reading a different imaginary document.

Writing the contract first is not bureaucracy. It is choosing one document before the system grows copies of itself.

What I put in the contract

Enough that two engineers can build in parallel without guessing:

  • routes, methods, and operation ids
  • request and response schemas
  • auth and permission expectations
  • error envelopes and important status codes
  • list contracts: filter, sort, cursor or page, totals
  • idempotency and side-effect notes when they matter

I do not need a novel. I need a spine. The Prisma model and the OpenAPI document should agree on the nouns. Generated clients and validators should come from that agreement, not from handwritten twins. 

product nouns
    ↓
schema + OpenAPI
    ↓
server handlers that implement the ops
    ↓
generated client / hooks
    ↓
UI that consumes the SDK

How the team order changes

Clarify stops being a meeting about vibes and becomes a meeting about shapes. Align happens on the contract. Implementers can stub the client against the spec while the server catches up. Reviewers can ask whether the diff matches the operation, not whether two people remembered the same field name.

When requirements change, the contract changes first. Then the generated pieces move. Then the hand-written logic. That order keeps the temporary code from becoming the source of truth by accident.

What about speed?

Spec-first looks slower for the first hour and faster for every hour after that. Vibe-coded endpoints feel quick until the third consumer appears and nobody can say what “success” returns.

For prototypes, a thin contract is still worth it. Even a short OpenAPI file with three operations beats a chat history and a hope. For production work, I treat an undocumented API as unfinished work, the same way I treat a missing test on a money path.

Write the contract before the code. Make the code a loyal implementation. Let everything else derive from that. That is how systems stay coherent when more than one person is touching them.
