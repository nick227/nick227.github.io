This article is a guide for testing turn-based realtime apps, using Poker Champ as the concrete example. Poker Champ is a Colyseus Texas Hold'em server with an Expo client. The hard problems are not the poker rules themselves — they are timers, reconnects, concurrent tables, and making sure money never drifts.

You will get the six test layers we use, the FakeClient pattern for driving rooms without a websocket server, the invariants that catch silent stalls, and the exact scripts to run each layer.

Why happy-path tests miss real bugs

A fold that passes in isolation does not prove the table works. Poker Champ has concurrent seats, street timers, queued auto-actions for disconnected players, and reconnect grace windows. The bugs that actually break games are races between those systems:

  • An auto-action queued for street N fires after the hand already moved to street N+1, mutating the wrong state. (dealer.auto-action-queue-race.test.ts)
  • A hand has no valid turn owner and no armed deadline, so it sits forever. The soak catches this as UNOWNED_ACTIVE_HAND.
  • A human leaves mid-hand, bots keep the room alive, and the table never advances. Stall monitors flag this as a ghost table.

The fix is layered testing with continuous invariants, not more happy-path cases.

1. Engine unit tests

Keep game rules out of the networking layer. In Poker Champ, Dealer is the authoritative engine and must not depend on PokerRoom. Unit tests cover betting, side pots, showdown, and money without sockets.

  • Side pots and uncalled returns — sidepots.integration.test.ts, sidepot.uncalled-return.integration.test.ts
  • All-in matrices — dealer.allin.matrix.6max.test.ts
  • Settlement money safety — settlement-service.money-safety.test.ts, money-invariants.test.ts
  • Street transitions — dealer.between-hands-lifecycle.integration.test.ts

Run them with pnpm test:server:core. When one fails, the bug is in the rules, not in networking.

2. Room integration with FakeClients

Most room tests do not need a WebSocket server. Create a PokerRoom, stub setMetadata, call onCreate, join FakeClients, emit actions, and assert on the TABLE_SNAPSHOT payloads the room sent. 

const room = new PokerRoom();
room.setMetadata = async () => {};
await room.onCreate({ tableConfig: { /* blinds, seats */ } });

const client = makeClient("c1"); // FakeClient: captures send() by type
await room.onJoin(client, { buyInCents: 10_000 }, { userId: "u1", username: "alice" });
room.onMessageEvents.emit("ACTION", client, { type: "FOLD", handId, actionId });
await flushAsync();

// Assert client.latestSnapshot: toActSeat, street, pot, stacks

Controls that keep these tests deterministic:

  • vi.useFakeTimers() for turn deadlines and between-hand delays
  • Stub CashierService and TableSeatSessionService so money IO does not hit the database
  • waitFor(condition, timeoutMs, label) instead of fixed sleeps — failures include the label so you know what stalled

Room scenarios covered this way: join guards (table-join.guard.test.ts), action broadcast and NOT_YOUR_TURN (table-action-broadcast.test.ts), reconnect timeouts (poker-room.reconnect-timeout.test.ts), session policy (session-policy.test.ts).

3. Soak and churn tests

Unit and room tests cover known cases. Soaks find the ones you did not think of. They run many hands with randomized legal actions, inject disconnect/reconnect mid-hand, and assert chip conservation after every settlement. If a hand stops progressing, the test fails with a trace of the last state changes.

  • Single-table dealer soak — dealer.random-walk.soak.test.ts. Runs via pnpm test:server:soak (SOAK_HANDS=50 by default).
  • Multi-table room soak — poker-room.multitable.soak.test.ts. Concurrent rooms, one human + one bot each, asserts no table goes quiet.
  • Churn matrix — multiplayer.churn.matrix.test.ts. Runs via pnpm test:server:churn:matrix.

Example of a bug only soaks catch: an auto-action queued for street N fires after the hand moved to street N+1, mutating the wrong state (dealer.auto-action-queue-race.test.ts). A single-hand unit test never hits this race.

4. Headless Colyseus harness

FakeClient tests skip the websocket layer. The headless harness boots a real Colyseus Server, creates rooms through matchMaker, and drives scripted clients over actual connections. Scripts: pnpm harness:headless (two-client) and pnpm harness:headless:churn (multiplayer).

Scenarios include fold-storm, allin-ladder, join-leave-thrash, and endurance. On failure the harness writes an event timeline and the violating invariant — enough to reproduce without re-running the full soak.

5. Playwright e2e

E2E checks that the client UI matches engine state across real browsers. Specs cover two-client stack consistency (two-player-stack-consistency.spec.ts), seat churn (churn-seat-dealin.spec.ts), rejoin/buy-in (rejoin-buyin-override.spec.ts), and tournament bust-out (tournament-bust.spec.ts). Keep this layer thin — it is slow. Do not retest side-pot math here.

6. Static analysis and contract gates

Non-runtime checks catch structural problems before they reach a room:

  • pnpm knip — unused exports and dead dependencies
  • pnpm fallow — unused code, duplication, complexity hotspots
  • pnpm madge — circular dependencies across server, client, and packages
  • pnpm sdk:check / pnpm api:shapes:check — generated client stays aligned with OpenAPI
  • pnpm realtime:check — shared Colyseus message schemas typecheck

pnpm verify runs all of these plus core server tests, soak, and the headless harness in one command. 

# Core confidence gate
pnpm verify

# Targeted soaks during hardening
pnpm test:server:soak
pnpm harness:headless:churn

# Nightly: full suite + extended soak budgets
pnpm test:all:nightly

The layer sections above already list the specific test files and the scenarios each one covers. Run pnpm verify before every merge. Run the nightly suite before releases. That is the full stack.
