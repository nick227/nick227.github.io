This article is a practical guide to thoroughly testing a time- and turn-based realtime app, grounded in Poker Champ: a Colyseus Texas Hold'em platform where seats, timers, pots, and reconnects all have to keep working together.

You will get the test layers that matter for Colyseus projects, concrete poker scenarios those layers catch, and a setup path you can copy for your own realtime rooms.

What you are actually proving

In a turn-based realtime game, “the rule is correct” is not enough. You also need continuous progress: someone eligible still owns the turn, streets still advance, timers still fire or get replaced by auto-actions, and money still conserves after every settlement. Players refresh, leave mid-turn, rejoin, open two tabs, and expect the table to stay fair anyway.

So the suite has to answer more than “can Alice fold once.” It has to answer: can randomized legal play, seat churn, and long runs keep completing hands without freezing or leaking chips?

1. Engine unit tests

Keep game rules out of the networking layer. In Poker Champ the Dealer owns deterministic engine behavior. Room code is glue. Unit tests hit betting rules, side pots, split pots, showdown order, and money conservation without sockets.

  • Side-pot builders and uncalled-return paths
  • All-in matrices and “no further action” short stacks
  • Settlement and ledger money-safety
  • Street transitions and between-hands lifecycle
  • Invariant helpers: assert money conservation, betting state, churn contracts

Tooling: Vitest on the server package. These tests should be fast and mean. When they fail, you know the rules broke, not the transport.

2. In-process Colyseus room tests

Most room tests should not need a real WebSocket server. Instantiate the room, stub metadata, call onCreate, join with FakeClients, emit messages, and assert on snapshots the room would have sent. 

// Pattern: drive PokerRoom in-process
const room = new PokerRoom();
room.setMetadata = async () => {};
await room.onCreate({ tableConfig: { /* blinds, seats */ } });

const sends = [];
const client = {
  sessionId: "c1",
  send: (type, payload) => sends.push({ type, payload }),
  leave: () => {},
};

await room.onJoin(client, { buyInCents: 10_000 }, { userId: "u1", username: "alice" });
room.onMessageEvents.emit("ACTION", client, { type: "FOLD", handId, actionId });

// Assert latest TABLE_SNAPSHOT: toActSeat, street, pot, stacks

Useful controls while testing time:

  • Fake timers for turn timeouts and between-hand delays
  • Disable or stub human turn schedulers when you want pure action-driven flow
  • Stub cashier / seat-session services so money IO stays deterministic
  • waitFor(() => condition) helpers instead of fixed sleeps alone

Poker scenarios that belong here: join guards, not-your-turn rejection, action broadcast, disconnect auto-fold/check, rejoin within grace, mid-hand joiners waiting for the next deal, ADD_BOT paths.

3. Soak, fuzz, and churn

Unit tests prove known cases. Soak tests hunt the unknown ones. Drive legal actions only, many hands, inject disconnect/reconnect, and check chip mass after every settlement. Fail if hands stop completing or tables stall.

  • Dealer random-walk soaks
  • Fuzz invariants on CI with a tighter budget
  • Multiplayer churn matrices: fold storms, all-in ladders, join/leave thrash
  • Multi-table isolation soaks across concurrent rooms

This is where timing bugs show up: an auto-action queued on one street gets discarded during an automatic street transition and never re-driven; the flop sits forever with nobody to act. A tidy one-shot unit test never races that queue. A soak does.

4. Headless Colyseus harness

Keep a thin runner that boots a real Colyseus Server, creates a poker room through matchMaker, and thrash-tests with scripted clients over websockets—still without a browser. Strict mode fails fast. Collect mode keeps going and writes repro artifacts: event timelines, diagnostics, the violation that ended the run.

Use this layer when FakeClient tests pass but you still distrust transport ordering, room disposal, or reconnect against the actual server stack.

5. Playwright e2e

Finally prove the client story matches the engine. Two-browser stack consistency, seat churn, rejoin and buy-in overrides, tournament bust-out, lessons runtime. E2E is expensive. Aim it at cross-layer contracts, not every side-pot branch you already cover in Vitest.

6. Static analysis and contract gates

Wire non-runtime gates into the same verify path:

  • Typecheck + ESLint
  • Dead code / structure: knip, fallow, madge, dependency-cruiser
  • OpenAPI / SDK shape checks so clients cannot invent fetch paths
  • Realtime contract typecheck for shared message schemas

In Poker Champ, pnpm verify chains the important gates before you pretend the table is shippable: SDK checks, client tests, server core, soak, headless harness, and static analysis.

Setup recipe for a Colyseus turn-based project

  1. Split engine from room. Pure state machine + invariants in testable modules. Room only adapts Colyseus clients and messages.
  2. Vitest for engine + FakeClient room tests. Snapshot-driven legal actions. Fake timers for timeouts.
  3. Define invariants early. Turn ownership, progress, money conservation, “hand must complete or explicitly abort.”
  4. Add soak/churn next. Randomized legal play and reconnect injection with completion-rate budgets.
  5. Add one headless real-server harness that dumps repro artifacts on failure.
  6. Add Playwright sparingly for UI/stack agreement.
  7. Put it behind one verify script and run the heavy soaks on a schedule or release gate. 
# Example gate shape (Poker Champ style)
pnpm test:server:core      # engine + critical room paths
pnpm test:server:soak      # random-walk / completion budgets
pnpm harness:headless      # real Colyseus churn
pnpm test:client:e2e:stack # Playwright stack consistency
pnpm verify                # contracts + static + core confidence

Poker scenarios to steal for your domain

Map these to your own turn game:

  • Illegal turn — reject actions from the wrong seat / stale handId
  • Disconnect on turn — auto-action or timeout path still advances the machine
  • Rejoin grace — seat and stack survive; late join waits for a clean boundary
  • Multi-instance isolation — table A cannot poison table B
  • Money or score conservation — totals match before and after settlement
  • Long-run completion rate — N hands or matches must finish above a budget

Thorough testing for turn-based Colyseus apps is a ladder: rules, room glue, chaos over time, real transport, UI agreement, then static gates. Start at the bottom, automate the ladder, and keep one command that refuses to ship a quiet stuck table.
