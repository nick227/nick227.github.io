This article is a deep dive into the coin change problem with an emphasis on dynamic programming: what DP actually is, what subproblem coin change is really solving, and how to spot that shape in other work.

You will get a plain definition of dynamic programming, a few ways to see the same solution, and an optimal bottom-up function for the classic unbounded coin change case.

What dynamic programming is

Dynamic programming is identifying overlapping subproblems, solving each one once, and reusing those answers instead of recomputing them. You define a smaller question whose answer helps the larger question. Then you store the smaller answer.

If a recursive solution keeps asking the same question with the same inputs, that is the signal. Memoization or a table turns repeated work into a lookup.

Coin change and the real subproblem

Classic setup: you have coin denominations and a target amount. You want the fewest coins that sum to that amount, or a signal that it is impossible. You may reuse a denomination as many times as you want.

The real subproblem is not “solve the whole amount from scratch every time.” It is: 

What is the fewest coins needed to make amount x?

Once you know the best answer for every smaller amount, the answer for x is: 

best(x) = 1 + min(best(x - coin)) for each coin <= x

That is the relationship. Every larger amount is built from a smaller amount plus one coin.

How to identify subproblems in any space

Ask what smaller version of the same question appears inside the big one. Good candidates usually share these traits:

  • the smaller answer has a clear meaning on its own
  • the same smaller answer is needed more than once
  • there is a rule that combines smaller answers into a larger one
  • you can order the work so dependencies are already finished

In coin change, amounts 0..target are the ordered subproblems. Amount 0 needs zero coins. Everything else depends on smaller amounts.

Same solution, multiple views

It helps to conceptualize the same idea more than one way so the relationship sticks.

Recursive view: to make amount, try each coin, then solve amount - coin. Cache those results so identical calls return immediately.

Table view: build an array minCoins[0..amount]. For each amount, try every coin and keep the minimum. You are filling the answers in increasing order.

Graph view: each amount is a node. A coin is an edge that moves you forward by that value at cost 1. Coin change is the shortest path from 0 to the target on that graph.

Same subproblems. Same recurrence. Different pictures of why reuse wins.

Optimal bottom-up version

function coinChange(coins, amount) {
  const INF = amount + 1;
  // minCoins[x] = fewest coins to make amount x
  const minCoins = Array(amount + 1).fill(INF);
  minCoins[0] = 0;

  for (let x = 1; x <= amount; x++) {
    for (const coin of coins) {
      if (coin <= x) {
        // make x by adding one coin onto a smaller solved amount
        minCoins[x] = Math.min(minCoins[x], minCoins[x - coin] + 1);
      }
    }
  }

  return minCoins[amount] >= INF ? -1 : minCoins[amount];
}

Each amount is solved once. Each coin is tried against that amount. The table reuses every smaller answer. That is dynamic programming in one screen: name the subproblem, order it, store it, combine it.
